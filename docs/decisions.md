# Decisions log

Decisions made by the studio on the CEO's instruction to decide on its own ("You can decide on your own will"), 2026-11-21.

1. **Epic figures stay off screen.** Missions use original mortal characters. Epic figures may be referred to briefly and respectfully, never shown or made targets. Reason: respect for living traditions, and it keeps the stories original.
2. **Grain-relief twist approved** for "Escape from Hastinapur": the courier's plea asks for grain relief and the gate captain opens the gate. No community is the villain.
3. **Player choices are deferred** until the engine supports branching. The screenplay keeps the two choices (back lanes or main road; cross now or wait a bell) for a later version.
4. **Sources checked.** Lal's 1100-800 BCE date for Hastinapur Period II is confirmed against his own chapter and a university summary. The 2021-22 excavation date (c. 1500-1000 BCE) comes from a Wikipedia summary of a report we have not read, so the game labels it "as reported". The Amrita essay is devotional, so it supports only the tradition, not history. A scholarly review is still recommended before a public launch.
5. **3D by default, 2D as fallback.** Three.js is vendored as a tree-shaken build. The performance claim for mid-range phones is unproven until tested on real devices.
6. **Mission 2 ("The Night Report of Pataliputra") decisions.** The informer may act as the reporter in the story. Branching stays deferred. The Mauryan-era theme is approved. A scholarly review is recommended before a public launch.
7. **Mission 2 winnability is only partly verified.** Tests assert that the route is reachable and guard paths avoid walls. A scripted bot wins with guards removed and also with guards on (health 12, 4 hits), but that bot ignores guards, so it is not proof a human can win. Real playtesting is needed.
8. **Visual identity: lapis night, marigold gold, sindoor red, peacock teal.** Title poster with a turning chakra and a Devanagari wordmark (system fonts only, no downloads), glass HUD, mission title card, glowing 3D night scene (lit windows, lamps, light-beam checkpoints, dust trail). Motion and flashes are off with reduce motion. The 2D fallback view still uses the older flat colours.
9. **Story frame and traveller.** The player chooses a traveller (female or male, six original looks, a name of up to 12 letters, an outfit colour) before the first mission, and can change it from the start screen. In the story the player walks the chakra of time and is the courier each era needs. Mission scripts use `{name}` for the player. The choice is kept in localStorage and checked when read.
10. **Look: anime-style people in a physically lit city.** People are cel shaded with outlines and large eyes (original designs, no existing characters). Buildings and ground use physically based materials, filmic tone mapping and an environment light, and desktops also get bloom (add `?fx=1` on a phone to try it). The three.js bundle now also contains the glTF loader, but authored character models are not hooked up yet.
11. **Levels are timeline events.** Each event on the time chakra is a level. The climb runs through the yugas in tradition's order (Satya, Treta, Dvapara, Kali) and ends in the Kalki era. The Kalki avatar is never shown, spoken or harmed on screen; the player is a courier and protector there too. The Kalki era is Tradition (prophesied) with Invented gameplay, a hopeful dawn, not a prediction.
12. **Progression from shunya.** The traveller starts with nothing and earns crouch, vault, staff, sword and bow by finishing levels, in that authored order. Violence is self-defence only. Blood is a brief small spatter with a Settings switch to turn it off. See docs/review/progression-architecture.md and docs/shunya-arc.md.
13. **Zoomable chakra, locked preview.** Capture as many events as we responsibly can in each yuga. The chakra zooms from all yugas, to one yuga's events, to one event and its year. Anyone can tap any event and read its introduction, but a level is playable only after succeeding at the one before it. Locked state is shown as text ("Locked: finish X first"), not colour alone.
14. **Reach is the status.** The excitement is climbing level by level through the yugas, so the furthest era a player has reached is their rank, and Kali Yuga then the Kalki era are the top. Plan: a rank title per era shown on the chakra and start screen, and a shareable "reached" card made in the browser. Shared rankings and any leaderboard need a server and anti-cheat, because a progress save in the browser can be edited. That is a later phase, not built yet and not possible on GitHub Pages alone.
15. **The chakra is the first screen.** A wheel of five yugas (Satya, Treta, Dvapara, Kali, Kalki era) drawn on a canvas, unfolding on load, with a glowing ring on the yuga the player is at (the yuga of the first built level not yet finished). Equal sectors on purpose: the wheel does not claim the lengths of the ages. Zoom has three steps (whole wheel, one yuga, close in) by buttons, keys (+, -, arrows, Page Up/Down, Enter, Escape), wheel, pinch and tap. The same events are always in a list beside or below the wheel (rows are virtualised: only visible rows exist in the DOM), and the wheel is a picture of that list, not the only way in. Reduced motion (system setting or the game's switch) turns off the unfolding, turning decoration, pulse and flights; every function stays. A `?mission=` link skips the chakra. The 3D view loads only after the player leaves the chakra.
16. **Lock rule on the chakra, and one deviation to confirm.** A level is playable when the level before it in `requires` is finished (progress in src/progress.js, keyed by mission id). Because most of the 22 levels are not built, a level that is built is gated by the nearest earlier level that is built, not by an unbuilt one (otherwise "Escape from Hastinapur" would be locked forever behind levels nobody can play). Unbuilt levels show "Coming soon: not playable yet"; info cards show "Info only: not playable yet". Locked cards can be read; Play stays focusable with aria-disabled and announces the lock. Objective completion is not tracked yet (progress stores only finished missions), so a keystone's objective cannot gate anything until it is built. NEEDS TPO/CEO CONFIRMATION.
17. **Data is sharded, one file per yuga, with a small index.** `data/events/index.json` (counts and a "spine" of all levels, so locks need no other shard) loads first; `data/events/<yuga>.json` loads when that yuga opens and is cached. Fields: id, yuga, year (or "Legend"), label, kind (History, Tradition or Invented), level, order, requires, mission, region, source, intro, needsReview, needsObjective, skill. `tools/check-events.mjs` (in verify.sh) rejects duplicate ids, a missing kind, year or source, an empty introduction, broken or looping `requires`, unknown missions and index/spine mismatches. The 58 seeded events carry the source note "docs/timeline-levels.md (studio draft, not yet checked against a primary source)": no event has been checked against a primary source. Region tags were added from the place names in the intro text and are unreviewed. One year was reworded: the Arthashastra's "Contested" became "c. 4th century BCE (traditional attribution, disputed)" so every event has a year or Legend; a reviewer should confirm.
18. **Reach counts: design for later, only a static file today.** The chakra shows "N players have reached this" from `getReachCounts()` in `src/chakra/reach.js`, which returns `{eventId: count}` or null. The only provider shipped reads an optional static `data/reach.json` (`{"counts": {"kal-l14": 12}}`); the file does not exist yet, so every card says "Be among the first". No number is ever made up, and zero is never shown. Intended privacy-safe design, NEEDS CEO DECISION ON HOSTING: a tiny backend that stores only anonymous per-event counters. The browser sends one request per player per event the first time that level is finished (it remembers locally that it has sent it), carrying only the event id: no account, no player id, no IP address stored, no cookies, no third-party scripts. The server adds 1 to that event's counter, rate-limits by IP in memory only (never written to disk) and refuses ids that are not in data/events. Counts are published as the same static JSON shape so the page needs no change. Known limit: because a browser can be edited, the counts can be inflated; they are a warm "you are not alone" signal, not a leaderboard (see item 14). No backend and no network call to third parties is built.
